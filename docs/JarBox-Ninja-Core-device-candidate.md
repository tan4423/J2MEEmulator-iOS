# Ninja Core device candidate — scoped screen-sink elision, not full slicing

The offline 30-wrapper residual proof-of-concept remains unintegrated. This device step removes screen-only raster and selected already-resolved Graphics draw wrappers at the existing VM boundary, without skipping game paint callbacks, stores, argument evaluation, setters, queries, network, tick, sync, offscreen Image work or changing JARs. Keep automatic mode 1, never re-enable old mode 8. Exact SHA gate is deliberately narrower than structural discovery: original NinjaSchool_251, Nick t5, TrungDucTV profiles 1/2/3; V9 NOKEY has reflection and remains compatible. All three actual archives were checked for no direct Graphics.getPixels/getNativeContext/copyArea, NativeBridge, reflection or DirectGraphics references and no bundled Java/LCDUI classes. Nick references Image.getRGB and all three reference Image.getGraphics; real offscreen drawing remains mandatory. No direct reentrant repaint/serviceRepaints/setCurrent/doPaint/flushBuffer references in prior potential paint graphs. These checks are not full effect proofs. Archive identity assumes app-managed JAR files are not concurrently replaced between recognition and class loading; not a security boundary.

On park, only known profile + recognized live Canvas and no compatible-only preference arm the candidate. At each full non-GameCanvas paint, no explicit buffer or previously detected pixel dependency, require actual simple Canvas structure. Keep the shared Graphics.headless flag false; native TLS scope exact VM generation and Canvas context suppresses screen raster on the invoking thread only. Existing native setters/query state remain normal. Existing interpreter elision accepts a narrower subset of exact bundled resolved Graphics methods for mode 1; drawChar/fillTriangle/drawRGB still follow ordinary Java code, argument evaluation retained for all calls. The native sink path can suppress raster in these calls too. Never elide game wrapper arithmetic yet. On resume mark full redraw via existing refresh handshake; stale scoped flush cannot publish. On detected pixel dependence or exceptional paint, reject sticky for that JVM, use full paint on later frames. An unexpected pixel dependency detected late can already have seen stale pixels; fallback is not proof or rollback of that frame. No claim that live gameplay or all native/library effects are preserved until device tests. No periodic double paint/canary, no render-only update state elimination, no whole-program slicing. Do not promote to production until real game progression and long-run tests pass.
