# Compatible paint fast paths — 26 November 2026

7465d34 device measurement: mode 0 approximately 38.97% process CPU (60.18 s), mode 1 approximately 40.46% (15.93 s); 406 measured paint calls, 36.55 CPU percentage points in paint, 407 font reuses. Different short intervals do not establish a regression or comparable speedup. Optimize actual paint work, not game behavior.

This candidate leaves all four experimental interpreter flags OFF for comparison. Compatible mode 1 extends the existing exact duplicate color, clip and stroke gates (clip still requires same raw rectangle, saved color and saved stroke). Pending CPU batches drain as before; replay is excluded. Font reuse retained. Region draws on the owned Canvas with valid immutable source and normal clip can reject completely outside sprites using the existing one-pixel conservative guard, after pending drawing drains. The other valid region draws reuse the very same CGImageCreateWithImageInRect result via a lazy 64-slot Canvas-local cache. Retain source and crop; exact identity and rectangle key; allocation failure/budget/collision preserve the reference draw. Charge full source backing and crop backing plus estimated metadata conservatively, cap at 1 MiB logical charge per Canvas including table. Actual Core Graphics memory may differ. Cache cleared in the same context teardown as live/batch cache, in both normal release and owner cleanup. Offscreen contexts, mutable images, invalid regions, replay, other modes retain old route. No direct software raster rollout, no whole-paint skip, no JIT, no tick/network/RMS changes. No shared mutable JVM data.

Counters compatible_crop_hits/misses, compatible_region_culls, compatible_state_reuses are local to Canvas and published per owner on existing flush; pending unflushed increments are not visible. Host test covers actual header with simulated CG ownership, collisions, exact keys, allocation failure, bounds and teardown; not actual Core Graphics rendering. CI and device validation required, including pixel comparison and long-running gameplay. No claimed CPU savings yet. Future work: measure impact and target actual native/Java hotspots; don't treat exact paint CPU as all avoidable.
